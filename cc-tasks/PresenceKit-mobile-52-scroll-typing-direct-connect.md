## 1. P0｜滚动策略：发送必达最新、浅聊天自动跟随、看历史绝不扰动

### 用户要的精确规则

- **主动按发送**（文本、引用、附件、语音转文字等实际提交消息）：**无论此前停在哪里，都立即恢复“跟随最新”并滚到自己刚发送的消息**。键盘弹起、输入栏改变高度时也应保持自己消息可见。不得仅在 `scrollController.following == true` 时才滚底。
- **用户没有在主动阅读历史**：如果目前在底部、接近底部，或者聊天总高度较短、不足一屏，收到角色的新消息、分段回复、贴纸或三点输入气泡时，**自然随内容增长往下滚**；不要只滚一次、后续新段落静止。
- **用户主动向上翻阅历史**：立即退出跟随，锁住可见消息的稳定 ID 和屏幕内偏移。后续 1/10/50 条新消息、历史补页、后台恢复、final/WS/HTTP 到达、typing 显隐、系统状态变更，都不得挪动阅读位置。仅在原有轻量“新消息/到最新”入口提示，不强行跳到底。
- **重新跟随**：用户主动发送消息、点击“最新”、明确滚回底部时恢复。页面浅且未发生主动上滑时视作跟随；不要单纯用 `distanceFromBottom <= 1` 这种过苛阈值决定行为，也不要因为键盘弹出造成被动距离变化就判定“正在读历史”。
- **主动刷新**不代表主动请求跳到底；刷新结果必须尊重当前阅读模式。异常重连同理。

### 指向当前已发现的问题

- #50 分支 `lib/controllers/chat_controller.dart` 的 `_enqueueOutgoing()` 在 `_renderOutgoing(row)` 后仍有 `if (scrollController.following) scrollToBottom()`；这会导致用户主动发送却不跳底。把发送作为明确的跟随意图，而不是普通网络消息。
- `ChatScrollController.following` 与 `_handleScroll()` 使用 `distanceFromBottom <= 1` / `pixels` 变化，容易把“略高于底部”“布局被动变动”“手势上滑”混淆。应建立可测试的用户滚动意图判别：滚动方向/手势、用户是否主动离开底部、近底阈值、短内容、键盘尺寸变化、自动跟随动画的内部滚动事件要区分。
- `AnchoredChatList` 的锚点保护必须保留；不要为了好跟随恢复旧式 `newMaxScrollExtent - oldMaxScrollExtent` 全局补偿。
- 去掉不同入口互相竞争的多个 `postFrame` 跳底任务；增加 scope/generation 校验，旧请求的回调不能在用户已上滑之后拉回底部。

|---|---|---|
| 52-A1 | 从三天前历史任意位置主动发送一句话 | 立刻转到新发送消息且持续跟随后续回复 |

## 2. P0｜恢复叶瑄「…」待机/输入中气泡，不许永久假装正在运行

### 用户感知目标

- **发送消息后**，在等待角色回应时，原有与角色头像、当前聊天主题一致的 `TypingHimMessage` / `JumpingDots` **「…」气泡应可见**；不使用新的系统提示框、长文字“服务器处理中”替代它。
- 收到最终回复时，三点自然结束，正式消息出现；多段回复间可以保留过渡，但绝不能叠多个三点气泡。
- 离开再回来、切后台、锁屏、应用进程重建后：服务端**可确证 running** 则恢复三点；已 completed 则补读最终消息并关闭三点；未知/断网/服务端重启不能无限显示“正在输入”，要在相应用户消息上给低干扰的“待确认/连接异常”状态及进入既有详情的操作。
- **本地刚发起请求到拿到服务端确认之间**可展示“等待回复”的视觉动画，但不得将其当作服务端已在执行的证明；若网络失败或到期，应自动收束，不得长期悬挂。这是对用户等待反馈的 UI 状态，与“可确证服务端 running”必须在控制器中分离。
- 不让“查询投递结果”“移出本机队列”等大技术按钮回到聊天时间线；仍复用 #50/#51 的二级详情安全恢复入口。

### 已知缺口与实现方向

- #50 现有 `_executeOutgoing()` 开头主动设 `himTyping = false`，最终 `finally` 仍设 false；#50 文档将“跨生命周期恢复三点”明确标为 open。先修本地 **等待回复 → 角色输入气泡** 的状态投影，再修真正 running 恢复，不能为了避免误报直接删掉所有三点。
- 审查 `ChatController` / `chat_session_coordinator.dart` / `chat_scene.dart` 与 `TypingHimMessage` 的状态来源；复用既有组件和视觉。将“本地正在等回包（有时限）”“远端确认正在执行”“已完成”“未知/失败”分开；单一稳定状态投影，避免从不同入口独立设置布尔值导致丢失。
- 查询是否已有可复用、按 **owner + char + domain + session + request_id** 限定的手机只读运行状态接口。**不能借用桌面管理员接口给手机，更不能为了显示三点就自动重发请求。** 如果确实缺接口，先把客户端的短时等待动画修好，并在交付中明确 `跨进程 running 恢复 BLOCKED`；如要跨仓增加只读接口，必须按当前工作树开展且由用户先确认后端修改范围，不创建后端新编号/新分支。
- 保留 `request_id` 幂等、Outbox 顺序与 skipped/outcomeUnknown 语义、final-only 与历史对账；后端结果一旦确认，不可生成第二条消息或再次调用工具。

| 52-B1 | 正常发送，服务端数秒后回复 | 发送后出现原样式三点气泡，回复出现时三点消失 |

## 3. P1｜手机和电脑不挂梯子也能访问后端（先找网络根因，优先配置方案）

### 目标与边界

- 当前用户反馈必须在手机/电脑开代理或 VPN 才能连上 OrangeVPS 的 PresenceKit。目标是 **两端关闭代理/VPN 后，正常网络直接使用同一个稳定的 HTTPS 入口访问后端**，且所有已存在的 Chat、WS、媒体、推送回源等必要链路不破坏。
- 这不是仅改客户端超时或把 `http://127.0.0.1:8080` 换成 VPS IP；不要假设“改了 Flutter 就能免梯子”。先分辨：DNS/AAAA 污染、运营商到海外 VPS 路由、VPS 防火墙、安全组、出口/入口端口、域名证书、反向代理、TLS/SNI、WebSocket Upgrade、客户端代理继承、Tailscale/内网地址依赖，以及是否只开放本机 127.0.0.1。
- **严禁**为了直连把 admin HTTP 接口、数据库、管理面、凭据或未认证服务直接暴露到互联网；不使用公共明文 HTTP，不关闭 SSL 校验，不把任何 token 写入 git、日志或截图，也不要求手机始终挂 VPN。

### 必须先做的只读排查

1. 梳理目前手机/桌面配置的 backend origin（去掉密钥），VPS 监听地址、反向代理（Caddy/Nginx/其他）、443/80 入站、防火墙和安全组、DNS A/AAAA、TLS 证书与服务端地址是否通过 Tailscale/代理才可达。
2. 对比**无 VPN 的手机移动网络、手机 Wi-Fi、Windows 本机网络**下域名解析、TCP 443、TLS 握手、HTTPS health/鉴权探测、WS Upgrade，以及开代理后对照组。不能只从 VPS 自身 `curl` 成功就宣称客户端直连成功。
3. 区分“网络根本不通”和“到达后鉴权不通”（401/403）及“WS 不通但 HTTP 通”；错误报告应用户可理解，详细技术信息只在设置诊断查看。
4. 若手机、电脑当前本身使用系统代理，确认是否错误地把后端流量强行送入代理；**仅在确证可直接访问且不会破坏其他路由时**做精准直连/绕过代理配置。

### 优先方案及实施权限

- **优先**复用已持有域名，为 VPS 提供标准的公网 **HTTPS 443** 入口，由成熟反向代理把必要 API 和 WS 转发到本地后端；保留已有的 TLS/鉴权/限流、防火墙及后端授权，证书自动续期。若已有反代/公网 HTTPS，优先修复现有配置而不是新建第二套。
- VPS 无法稳定入站或路由被运营商阻断时，提交故障证据与备选方案（例如托管隧道/可靠的可达中继入口或迁移到可直连线路的服务商）；**这些是可从客户端无需 VPN 使用的入口，不是暗中让用户继续挂梯子**。不要承诺对所有网络/运营商 100% 可达。
- 正式修改 VPS DNS、防火墙、Nginx/Caddy、证书或生产域名之前，先提交具体变更清单与可回滚方案供用户确认；严禁自行关闭或替换正在工作的入口。客户端支持可达的 HTTPS origin，保留原节点配置和回退。
- 现有 `BackendSecurityPolicy`、scoped mobile token、回源身份、WS 鉴权必须保留；业务 API 不应被变成匿名公共服务。桌面客户端也要做直连可用性核验，但不因本单扩展大量桌面 UI 改造。
