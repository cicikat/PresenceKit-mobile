## 0. 现场证据与用户原话（必须先复现）

- 见 `evidence/mobile50_queue_state.jpg`：正常聊天中出现两条巨大绿色技术操作「查询投递结果」「移出本机队列」，对话被大空白切断；输入框上方又有低对比度「正在刷新新消息…」spinner。不可接受。
- 清后台再启动后依旧出现技术状态，队列停滞；服务器卡顿时连续发送多条，**都显示进入队列但不送达，也无明确恢复操作**；用户不知道连接到底好没好、模型是否正在处理。
- 曾有的角色待机/输入中反馈消失：一卡就没有三点/等待表现，也没有故障原因；不能以一个无限转圈代替真实状态。
- 用户认真阅读旧聊天时，新消息、补读或刷新会把阅读位置强行向下拉；用户明确**不想看新消息**，更不想被自动带到底部。
- 本单覆盖此前 #310 文档提出但尚未落地的视口锚点、请求状态恢复、对话去技术化、设备感知入口和中继通知降噪；以手机 **#50** 为唯一实施编号。

## 1. 当前源码中已经能确认的问题（不要把推测写成真机复现）

1. **队列首项阻塞**：`lib/controllers/chat_controller.dart` `_drainOutbox()`（约 938–958 行）取 `rows.first`，只要其状态不是 `queued` 就 `break`；`_restoreOutbox()`（约 868–885）会把被中断的 `sending` 展示为 `outcomeUnknown`。这可以解释“首条不确定，后面的全站住”这一**机制**，但需使用用户 APK/真机日志确认本次是否由它触发。
2. **错误/排队的错误重试可见性**：`_retryOutgoing()`（约 548–572）对 `outcomeUnknown` 只 `refreshConnection()`；对 `retryableFailed/blocked` 才尝试回到 `queued`。界面不告诉用户为什么点了没用；`blocked` 不等于安全可重试，必须审计 401/403/413/422 等错误语义。
3. **多次点击会产生多个请求**：`_enqueueOutgoing()`（约 831–866）每次调用都 `mintRequestId()`，因此短时间多次点击同样文字可能形成多个独立待发条目；需区分用户有意连续发送与重复点击/重复事件回调，不能简单按文案永久去重。
4. **待机/三点依赖前台请求**：`_executeOutgoing()` 约 960–1078 令 `himTyping=true`，在 `finally` 置 false；重启时无可靠服务端 `running` 证明。当前 `mobile_realtime_controller.dart` 处理 `final_only`，不能从 WebSocket 已连接推断模型正在生成。
5. **强制滚动入口多头**：`loadOlderHistory()` / `_revealOlder()` 以 `newMaxScrollExtent-oldMaxScrollExtent+oldPixels` 补偿；`_followIncoming()` 的 post-frame 回调可 `jumpTo(maxScrollExtent)`；`_enqueueOutgoing()` 直接 `scrollToBottom()`；`ChatScene` 顶部的动态 metaRows 也改变列表几何。需要统一锚点与用户阅读意图。
6. **工程 UI 泄露到聊天**：`chat_scene.dart` 直接显示 `chatOutboxUnknown`、`chatWaitingReply`、`mobileError`、`outboxError` 等 meta；`chat_widgets.dart` 直接渲染恢复/移出队列按钮。`edge_refresh.dart` 另有刷新的 spinner，和角色输入、网络诊断没有区分。
7. **连接通道不是一个布尔值**：前台 HTTP/WS、后台 ntfy SSE、FCM、inbox/ACK 各有职责；没有证据时不能用一个「已连接」掩盖接收失败。`MobileNotificationService.kt` 的 `activateRelayConsumer()` 每次连接会 `updateForegroundNotification("中继已连接")`，未见同状态内容去重；`setOnlyAlertOnce(true)` 只能减轻提醒，不能说明系统通知没有被反复更新。
8. **传感器入口仍有静默隐藏**：`ambient_permissions.dart` 读取失败将 `_settings=null` 并返回 `SizedBox.shrink()`；用户无法知道功能为何消失。此前新增 light/motion/usage 不代表所有能力都可见或生效。

## 2. P0-A｜让发送队列永远有解释、有出口，而不是“站死”

**实现要求**

- 将本地出站状态机和网络结果拆开：至少区分 `已保存待发`、`发送中`、`服务端确认正在执行`、`送达/已完成`、`失败可安全重试`、`需要用户处理`、`结果待确认`、`离线暂停`。状态名称可以调整，语义必须明确；单个请求在 UI、持久化层、后端 receipt 中都能通过原 `request_id` 对账。
- **首条 `outcomeUnknown` 不得无限静默阻挡整队**。按原因显示「上一条消息尚未确认，后续 X 条已保存在本机、暂未发送」。允许单独 **检查状态**，在安全可证时恢复；对无法证明安全重试的条目，提供明确的 **保留等待 / 明确跳过此条并继续后续 / 移出本机待发**，并解释“跳过/移出不等于服务器撤回，后续仍可能出现回复”。不能自动越过不确定条目破坏会话顺序。
- 后续消息仍要能正常写入持久队列，**既不能谎报已发送，也不能在用户不知情时自动积压十几条**。在待发达到阈值或阻塞超过合理时间时，用一次低干扰提醒展示队列数及可操作入口；不反复弹出。
- 安全重试使用**原 request_id + 原载荷快照**且先检查后端证据；仅在明确没有执行、或服务器提供幂等保证时允许自动恢复。401/403/413/422 必须先处理鉴权/权限/载荷问题，不能机械地重新入队成死循环。严禁因网络超时重新执行可能有副作用的工具。
- 单次发送 UI 事件应具有入队幂等保护（同一按钮点击、软键盘提交、双击不得触发两次本机入队）。对于用户短时间**主动再次发送完全相同内容**，不永久吞消息，可用短暂确认或明显的“再次发送”动作；不同文本/引用/附件不得误去重。
- 断网/后端拥塞/HTTP 超时/应用进后台/系统杀进程/恢复/切账号或角色时：队列和草稿不丢、不乱序、不重复、不跨 owner/char/scope 串单。重启先恢复落盘，再做 scoped status/receipt 核对，最后才继续安全发送。
- 提供一个可用但不占聊天正文的「待发消息」界面：顺序、时间、每条真实状态、是否阻塞后续、查看错误、检查、撤销本机待发、明确重试；错误文案可理解，另有可复制的脱敏技术细节。

**关键禁止项**：不能用 `rows.dropWhile(...)` 偷偷跳过未知请求，也不能用清空 Outbox、删除 history、重建安装数据或直接加长 timeout 来冒充修复。

## 3. P0-B｜恢复角色待机/输入中反馈与可判断的连接状态

- 角色原有**待机视觉/在场状态**应恢复，不因等待网络请求而整块消失。必须区分：`平静待机`（没有在执行的证据）、`正在回应`（服务端 running 可证）、`等待网络确认`、`暂时离线`、`需要处理的发送失败`；不要把“本机队列中”装成叶瑄在思考。
- 真实服务器证实正在执行时显示现有 `TypingHimMessage` / 三点动画，和角色气泡/主题一致；退出页面再回、切后台再回以及进程被系统回收后重开都尽可能恢复；一旦完成显示**唯一**回复、取消三点，不能重复工具/重复消息。
- 如果后端现无足以证明 `request_id` running 的只读接口，先分析现有 receipt、session、final 投影并给出**独立后端依赖清单与安全 API 契约**（owner/char/domain/session/request_id 权限约束，只读，状态 `running/completed/failed/retryable_failed/unknown`）。不要在手机 #50 里擅自分配后端工单编号，也不要拿本机 loading 伪造已执行。
- 缺服务端证明、超时或重启导致状态 `unknown` 时，用户看见低调的「正在确认状态」/「未能确认，点此检查」而不是永久三点/永久 spinner；提供下次重试的操作和到期停止策略，不能永远转圈。
- 聊天页固定、轻量、**不占历史列表高度**地显示实际连接结果：例如 `已连接` / `连接不稳定` / `离线` / `正在重连`；可点击查看 `后端 API 可达性`、`发送通道`、`前台实时 WS`、`后台接收 FCM/SSE`、`最近成功同步时间`、`最后错误与处理建议`。不应把“中继已连接”当作“整个应用可以收发”。
- 连接状态必须有新鲜度、超时和降级机制：API 可达而 WS 断开应显示“实时接收降级”，而不是全局离线；HTTP 请求中断不能自动说“发送失败”；未知不冒充在线。不要显示 token、敏感正文、角色私有信息。
- `EdgeRefresh` 只在用户主动拉动或主动点刷新时显示短暂、清晰的进度；后台自动补读不得在聊天正文插入「正在刷新新消息…」。刷新失败要能结束并提示重试，不能遮挡输入框或反复引发布局变化。

## 4. P0-C｜彻底重做聊天技术状态 UI，保留救援能力

- **从普通聊天时间线彻底移除**大块「查询投递结果」「移出本机队列」「已送到后端」「后台收到 N 条」「正在刷新新消息」以及原始后端异常。不是只换颜色或把它们挪到其他空白位置。
- 普通聊天只保留用户/角色的消息气泡、必要的单条发送状态（小图标或一行简短中文）、角色三点和非侵入性新消息提示。`系统错误`、`队列编号`、`网络细节` 放对应消息的详情底部弹层或「连接与发送诊断」页；详情必须真的可用，不是隐藏功能。
- 所有失败/不确定状态都应有**用户一眼能理解的解释与可用操作**。例：`尚未送出 · 网络未连接`、`这条是否送达还不确定 · 检查`、`需要重新登录`；不能只显示空转圈或“处理中”。
- 弹层操作分清 **检查结果 / 重新发送 / 仅移出本机待发**；对有风险操作提供准确说明，但不做多余全屏工程对话框。新状态区不能撑开巨大的黑色空白。
- 不重新设计既有聊天主题的字体、壁纸、气泡色、角色头像和 Dream；各主题下的状态配色与对比度要可读。截图中绿色按钮和极低对比度 spinner 必须消失。

## 5. P0-D｜历史阅读位置必须绝对尊重用户

- 实现**统一 viewport anchor**：当用户离开底部开始回看旧消息，就进入“历史阅读模式”；保存当前第一条真实可见消息的稳定 `turn_id/msg_id` + 视口内相对偏移；消息插入/替换、补页、去重、网络状态变化、后台恢复后仍保持**同一气泡在屏幕同一位置**。
- 阅读模式中：收到新消息 1/10/50 条、角色工具完成、Outbox 状态变化、刷新、历史分段、加载更早消息、离线重连，都**不得跳底、自动滑一截、或把页面挤下去**。只能显示小型「新消息 ×N」提示；只有用户主动点它或主动滚到底才恢复跟随。
- 用户在历史位置点击发送，也不能在未确认前强制跳底；输入完成后按既有交互可提供「查看刚发送的消息」入口，但尊重仍在阅读旧消息的意图。
- 将 `loadOlderHistory()`、`_revealOlder()`、`_followIncoming()`、`scrollToBottom()`、`EdgeRefresh`、HTTP/WS/FCM 补读接入统一滚动协调器；移除相互竞争的 post-frame `jumpTo`。不要再用全列表 `maxScrollExtent` 差值混算顶部、底部和 meta 高度。
- 锚点被实际删除/合并时，以同段最近仍存在的稳定气泡恢复，不得默认跳到最新。首入空聊天页和用户明确滚至底部时正常跟随；大历史分页仍保持虚拟列表性能。

## 6. P1-E｜权限入口与后台通知收尾（承接旧需求，不得挤占 P0）

- 设置页提供易发现的「设备感知与权限」入口。实际已经实现的电池/步数/光照/姿态/使用情况访问/屏幕上下文/后台接收等能力，分别展示：支持性、系统授权、本机开关、后端有效状态、最近成功上报与错误。未实现的传感器不假装已具备。
- `AmbientPermissions` 原生通道失败不得 `SizedBox.shrink()` 静默消失；展示“不可用/读取失败/去设置或重试”。系统授权返回后状态刷新，不偷偷开启传感器。
- SSE/FCM/前后台启停审计：同文案、同状态的常驻通知不应每次重连都 `NotificationManager.notify`；加入状态去重与适度重连宽限，**保留真实角色消息通知**、Android 系统必须存在的前台服务通知和正确故障状态。不通过关通知、砍后台接收或破坏通知频道来降噪。
- 缺少 Firebase 配置或 Google Play Services 时明确提示 FCM 不可用/未配置，并说明其他接收通道是否有效；不能显示假“已连接”。

## 8. 执行顺序与交付要求

1. **只读定位**：核对当前 GitHub、Windows 本地、已安装 APK 版本和后台协议；复现并填写每项「代码事实/设备事实/推测」；保留原始数据。不要先改 UI。

4. **回归、真机验收、提交**：提供独立小提交与 PR，输出缺陷根因矩阵、测试视频/截图、真机通过项、未通过项、后端依赖、剩余风险和回滚方式。
